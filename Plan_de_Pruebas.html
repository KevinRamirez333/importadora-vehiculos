Plan de Pruebas

Sistema de Gestión — Importadora de Vehículos

Versión 1.0  |  Junio 2026

1. Introducción

El presente documento describe el plan de pruebas definido para el sistema, detallando las pruebas unitarias e integración identificadas para garantizar la calidad y correcto funcionamiento de los módulos desarrollados.

El sistema está compuesto por un backend en Node.js + TypeScript organizado en capas (Services, Controllers, Repository) y un frontend en Vue.js + TypeScript organizado en Views, Helpers y Components.

2. Alcance

Las pruebas cubren los siguientes niveles:

Nivel Cantidad Capa objetivo
Unitaria 5 pruebas Services (backend) y Helpers (frontend)
Integración 5 pruebas Controller + Service + Repository / View + Components

3. Pruebas Unitarias

Las pruebas unitarias validan el comportamiento de una unidad de código de forma aislada, reemplazando dependencias externas con mocks o stubs. Se enfocan principalmente en la capa Services del backend y en las funciones Helpers del frontend.

PU-01   Cálculo del precio total de costos de un vehículo (Service)

Módulo: Backend — Services
Descripción: Verificar que el servicio calcula correctamente el precio total de un vehículo sumando todos sus costos asociados: taller, traspaso, impuesto, placas y otros. El resultado debe ser la suma exacta de todos esos conceptos.
Precondiciones: Se proporciona un objeto con los valores individuales de cada costo (taller, traspaso, impuesto, placas, otro). No requiere conexión a base de datos (se usa mock del repositorio).
Criterio de éxito: El precio total retornado coincide con la suma de taller + traspaso + impuesto + placas + otro para distintas combinaciones de valores de entrada, incluyendo el caso donde alguno de los conceptos es cero.
Herramienta sugerida: Jest + ts-jest

PU-02   Verificación de disponibilidad del vehículo antes de realizar una venta (Service)

Módulo: Backend — Services
Descripción: Verificar que el servicio de ventas, antes de procesar o al momento de registrar una venta, consulta el estado del vehículo y determina si está disponible para vender. Si el vehículo no está disponible (ya vendido, anulado u otro estado que lo impida), el servicio debe rechazar la operación.
Precondiciones: El repositorio de vehículos se reemplaza con un mock que retorna distintos estados del vehículo (disponible / no disponible).
Criterio de éxito: Cuando el vehículo está disponible, el servicio permite continuar con el proceso de venta. Cuando no está disponible, el servicio lanza la excepción o error correspondiente sin registrar la venta.
Herramienta sugerida: Jest + ts-jest

PU-03   Exclusión de ingresos anulados en el cálculo del precio de venta (Service)

Módulo: Backend — Services
Descripción: Verificar que el servicio, al calcular el precio de venta de un vehículo, únicamente toma en cuenta los registros de ingreso que están activos/disponibles. Los registros de ingreso que se encuentren anulados (desactivados) deben ser ignorados en el cálculo, aunque cuenten con precio de ingreso registrado.
Precondiciones: Se proporciona al servicio una lista de registros de ingreso del vehículo, donde algunos tienen estado activo y otros están anulados, todos con precio de ingreso definido. El repositorio se reemplaza con un mock.
Criterio de éxito: El precio resultante corresponde únicamente a la suma o cálculo sobre los registros activos. Los registros anulados no modifican el resultado, independientemente del precio de ingreso que tengan registrado.
Herramienta sugerida: Jest + ts-jest

PU-04   Formateo de moneda en helper del frontend (Helper)

Módulo: Frontend — Helpers
Descripción: Verificar que la función helper formatCurrency transforma correctamente un valor numérico al formato de moneda local (ej. "Q 1,500.00"), incluyendo casos borde como valores negativos y cero.
Precondiciones: Función pura sin dependencias externas.
Criterio de éxito: La cadena retornada coincide con el formato esperado para cada valor de entrada probado.
Herramienta sugerida: Vitest

PU-05   Validación de formato de fecha en helper (Helper)

Módulo: Frontend — Helpers
Descripción: Verificar que el helper formatDate convierte una cadena ISO-8601 a un formato legible (ej. "01/06/2026"), y que retorna un valor por defecto cuando recibe una fecha inválida o nula.
Precondiciones: Función pura, se prueba con fechas válidas, inválidas y valor nulo.
Criterio de éxito: Salida formateada correcta para fechas válidas; cadena de fallback para entradas inválidas.
Herramienta sugerida: Vitest

4. Pruebas de Integración

Las pruebas de integración validan la comunicación entre múltiples capas o módulos del sistema. En el backend comprueban el flujo completo Controller → Service → Repository; en el frontend validan la interacción entre Views y Components.

PI-01   Registro de vehículo (Controller → Service → Repository)

Módulo: Backend — Controller / Service / Repository
Descripción: Verificar que al realizar una petición POST al endpoint de creación de vehículos, el controller delega correctamente al service, y este persiste la entidad mediante el repository, retornando la entidad creada con su ID asignado.
Precondiciones: Base de datos de prueba inicializada con schema limpio. Datos de vehículo válidos en el cuerpo de la petición.
Criterio de éxito: Respuesta HTTP 201 con el cuerpo que incluye el ID generado y los datos enviados. El registro existe en la base de datos de prueba.
Herramienta sugerida: Supertest + Jest, base de datos SQLite en memoria o contenedor Docker

PI-02   Búsqueda y listado correcto de vehículos (Controller → Service → Repository)

Módulo: Backend — Controller / Service / Repository
Descripción: Verificar que el endpoint GET de vehículos, al recibir criterios de búsqueda (como marca, modelo u otro filtro disponible), retorna correctamente todos los vehículos que coincidan con dichos criterios, pasando por las tres capas sin pérdida ni alteración de datos.
Precondiciones: Base de datos de prueba con varios vehículos pre-insertados de distintas marcas y modelos. Se realizan peticiones con diferentes criterios de búsqueda.
Criterio de éxito: Respuesta HTTP 200 con todos los vehículos que coinciden con el criterio de búsqueda, sin registros de más ni de menos. Una búsqueda sin filtros retorna todos los vehículos disponibles.
Herramienta sugerida: Supertest + Jest

PI-03   Creación de vehículo y visualización correcta en el frontend (Backend → Frontend)

Módulo: Backend (Controller / Service / Repository) + Frontend (View)
Descripción: Verificar el flujo completo desde la creación de un vehículo en el backend hasta su correcta visualización en el frontend. Al registrar un vehículo mediante el endpoint POST, el registro debe persistirse y posteriormente la vista del frontend debe ser capaz de recuperarlo y mostrarlo con todos sus datos correctamente.
Precondiciones: Backend levantado con base de datos de prueba. Frontend con la API apuntando al entorno de prueba. Datos válidos del vehículo preparados para el registro.
Criterio de éxito: El vehículo se crea exitosamente (respuesta HTTP 201). Al consultar el listado o la vista correspondiente en el frontend, el vehículo recién creado aparece con todos los campos correctamente desplegados, sin datos faltantes ni transformaciones incorrectas.
Herramienta sugerida: Supertest + Jest (backend) / Vitest + Vue Test Utils (frontend)

PI-04   Vista de costos de vehículo con componente de alerta ante error (View → Component)

Módulo: Frontend — Views / Components
Descripción: Verificar que la vista de costos del vehículo, al recibir un error en la carga de datos desde la API, muestra correctamente el componente de alerta modal con el mensaje de error correspondiente, sin romper la vista ni dejar al usuario sin retroalimentación.
Precondiciones: La llamada a la API desde la vista de costos se intercepta con un mock que retorna error. Componente de alerta registrado y disponible en la aplicación.
Criterio de éxito: El componente de alerta es visible en el DOM con el mensaje de error esperado después de que la petición falla. La vista no muestra datos parciales ni queda en estado de carga indefinido.
Herramienta sugerida: Vitest + Vue Test Utils

PI-05   Flujo de login y redirección protegida (View → Helper → API)

Módulo: Frontend — Views / Helpers
Descripción: Verificar que al ingresar credenciales correctas en la vista de login, el helper de autenticación almacena el token recibido y el router redirige al usuario a la vista principal protegida. Ante credenciales incorrectas, se muestra el componente de alerta de error.
Precondiciones: Endpoint de autenticación del backend mockeado con respuestas de éxito y error. Vue Router configurado con guardias de navegación.
Criterio de éxito: Credenciales válidas redirigen a la ruta protegida y el token se almacena. Credenciales inválidas mantienen al usuario en la vista de login y muestran la alerta de error.
Herramienta sugerida: Vitest + Vue Test Utils + Vue Router
